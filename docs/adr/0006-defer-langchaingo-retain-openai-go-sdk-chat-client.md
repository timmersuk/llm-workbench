# Defer langchaingo adoption for chat client; retain an unwired openai-go SDK implementation

Evaluated two alternative `chat.ChatClient` implementations against the existing hand-rolled `internal/chat/client.go`: one built on `github.com/tmc/langchaingo`, one on the official `github.com/openai/openai-go` SDK. Decided not to adopt langchaingo: it pulls in a comparatively heavy dependency tree (tiktoken-go, gjson/sjson, regexp2, uuid, etc.) for a single OpenAI-compatible provider, has no incremental access to streamed tool-call fragments (only the fully-assembled list once the call completes), has no typed `ListModels`, and — critically — reuses the same streaming callback for both text content and tool-call JSON fragments with no way to tell them apart, forcing a JSON-sniffing heuristic to keep tool-call data from leaking into streamed content. That last point is an ongoing fragility surface, not a one-time cost.

The openai-go SDK client fared better — a real incremental streaming iterator, correct per-fragment tool-call deltas (matching the native client's fidelity), typed errors (`*openai.Error`), a typed `Models.List`, and a lean dependency footprint — but wasn't adopted as the active implementation either: it recovers the LM Studio/llama.cpp `reasoning_content` streaming extension (which this workbench depends on, see `docs/adr/0004-chat-client-openai-compatible-wire-format.md`) only via each response chunk's preserved raw JSON, since that field isn't part of the official OpenAI schema — a working but non-typed escape hatch, versus the native client's first-class support. `internal/chat/client_openai_sdk.go` (`NewOpenAISDKClient`) is kept in the tree, compiled and tested, but not wired into `cmd/server/main.go` — worth revisiting if this workbench ever needs to talk to real hosted OpenAI, wants typed error handling, or needs a typed model-listing call badly enough to trade away the native client's tighter `reasoning_content` support.
