# Structure `context.yaml`'s verification entries instead of leaving them as bare strings

`context.yaml`'s `verification: []` field has been a plain `[]string` since Milestone 4 — a list of human-readable verification steps a GrillMe conversation produces, with no further structure. Milestone 6's Review mechanism needs to walk this list and, for each entry, either attempt it directly (hitting an endpoint, running a command, driving a UI check) or hand it to the human to perform themselves, only recording their confirmation. Those are two different code paths, and nothing in a bare string tells Review which one applies.

We widened each entry from a string to a structured `{description, kind}` object, where `kind` is `agent_executable | human_judgment`, rather than adding a side-channel (e.g. a separate list of "which indices are agent-executable") or inferring it heuristically from the text at review time. GrillMe is still the thing that authors this list — Review is just the first consumer of `kind` — so the classification is made once, at the point a human is already reviewing the draft context, rather than re-derived (unreliably) every time a review runs.

This is a genuine schema migration on a field that's been stable for two milestones, motivated by a need (agent-executable vs. human-judgment routing) that didn't exist when the field was designed. `RequirementsDraft.Context.Verification`, `drafttool.ProposeContext`'s JSON schema, and `FinalizeRequirements`'s handling of the field (`internal/task/lifecycle.go:39`) all change together. We accepted the migration cost now, while only one milestone's worth of tasks exist against the old shape, rather than defer it and let more data accumulate against a schema we already know needs to change — and rather than bolt on a separate classification list that would drift from the verification steps it's meant to describe.

This is the precedent for how future `context.yaml`/`plan.yaml` schema-narrowing decisions in this repo should be justified: prefer additive object-ification of an existing field (turning a bare string into `{description, kind}`) over a new parallel top-level field, when the new information is really a property of each existing entry rather than a separate concern.
