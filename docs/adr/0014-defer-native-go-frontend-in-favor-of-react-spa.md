# Defer a native Go frontend; keep the React SPA for now

Discussed replacing `frontend/` (React 19 + TypeScript SPA, embedded via `go:embed` into the server binary per `internal/web/assets.go`) with a genuinely native Go GUI, motivated by the eventual transition from server/webapp to a standalone application (see the background-service-plus-systray direction noted for `cmd/server/main.go`). The explicit goal was avoiding the "common" Electron/Tauri-style path of wrapping the existing web UI in a webview — i.e. not shipping TypeScript and calling it native.

**Toolkit survey**: `fyne.io/fyne` (pure Go, own OpenGL-rendered widget set, no webview, cross-platform incl. mobile) is the pragmatic choice if this is pursued — `gioui.org/gio` is more minimal/immediate-mode with less batteries-included; `Wails` and `lxn/walk` were ruled out early (Wails is a webview wrapper like Tauri, just Go-backed; Walk is Windows-only native widgets, which cuts against "standalone" cross-platform).

**The blocking tradeoff is testing maturity, not UI capability.** Fyne's `fyne.io/fyne/v2/test` package gives a headless in-memory driver for simulating input and asserting widget state via ordinary `go test` — comparable rigor to this repo's existing Go test suite for view-model/state-machine logic. It also has `test.AssertImageMatches` for golden-image snapshot testing, but that's materially weaker than the current `frontend/` stack's Vitest + Playwright: no auto-waiting, no trace viewer, no network interception, and pixel-snapshot brittleness across OS/GPU rendering differences. The gap isn't "can Claude/a human write correct Fyne code" — it's that verifying an implementation actually renders and behaves correctly shifts from automated E2E to manual/screenshot-driven checks, which is a real ongoing cost across roughly 7-8 screens (Projects, Task Kanban + detail, Requirements/GrillMe, Planning Mode, Review + diff, Execute log, Chat).

No existing CLI in `cmd/` (`server`, `draftmcp`, `modelprobe`) exercises task/project/review business logic independently of `internal/api`'s HTTP handlers — that logic lives in `internal/project`, `internal/task`, `internal/agentrunner` and would need to be driven either directly (in-process, bypassing HTTP+SSE entirely) or by keeping the existing REST+SSE API and writing a Fyne client against it. The former is more "native" in spirit; the latter reuses more of the current server as-is.

Considered building a Fyne prototype now — deferred, not rejected: revisit when the server/systray standalone transition becomes concrete, and treat the testing-maturity gap as a scoping question at that point (e.g., keep state/transition logic under ordinary `go test` coverage, accept manual verification for rendering, and decide then whether Fyne's snapshot testing is worth investing in or whether a smaller manually-verified surface is acceptable for an internal tool). If automated E2E/visual-regression confidence turns out to be non-negotiable, the fallback is Wails — explicitly the webview "bodge" being avoided here, trading away the native-Go goal to keep the mature Vitest/Playwright stack already proven in `frontend/`.
