# Tiered tool-activity disclosure, live-mode collapsing, and a bounded auto-scrolling panel; partially revises ADR-0018

`StageConversationPanel.tsx` and `ExecutePanel.tsx` render tool activity independently, with no shared code, and both have grown rough edges: `StageConversationPanel` shows every call/result in a live turn as its own chip forever (ADR-0018's deliberate choice), `ExecutePanel` never collapses at all — live or historical — so a long autonomous run accumulates an ever-growing flat list of chips. Neither panel bounds its own height or scrolls independently; both just grow the page. And once a chip is expanded, it shows the *entire* untruncated result inline — there's no smaller, scannable middle ground between "collapsed to a count" and "full text dump."

We're extracting a shared rendering layer (`frontend/src/ToolActivity.tsx`: `ToolActivityEntry`, `ToolActivityRow`, `ToolActivitySequence`) used by both panels, while leaving their underlying data feeds untouched — `StageConversationPanel` still bundles one `ConversationToolActivity[]` per turn, `ExecutePanel` still gets a flat SSE trace. The only change to `ExecutePanel`'s frontend state is grouping that flat trace into blocks (`{kind: 'text'} | {kind: 'tools', activities}`) so consecutive tool calls/results (a **sequence**) render as one unit; a sequence boundary is any interleaved assistant text, matching how a Conversation turn is already one sequence by construction (tool activity is bundled onto a single closing assistant message, never interleaved with turn text).

Three-tier disclosure, applied uniformly:
1. **Summary** (closed sequence, or already-collapsed live overflow): a plain count — `Used N tools` — plus an error indicator if any call in the group failed. Deliberately not broken down by tool name; a breakdown just duplicates the list one click away.
2. **List** (expanded from the summary): one row per call — tool name, a generic truncated one-line preview of its *arguments* (not its result — arguments are usually short and say what ran; results vary wildly in size and are exactly the noise this tier hides), and a status glyph (✓ / ✕ / pending) surfacing `IsError`, which previously had **zero** visual treatment anywhere in the frontend despite being tracked in the data model since ADR-0017.
3. **Drill-in** (expanding a row): pretty-printed JSON arguments and the full result, plain monospace text — never piped through the markdown renderer, since arbitrary tool output (file contents, command output) isn't authored as markdown and could be misinterpreted. Fidelity differs live vs. historical only because the underlying data does: a live call holds whatever untruncated content arrived over SSE, and a reloaded/historical call only has what survived `TruncateForPersistence`'s existing 2KB-per-call cap (`internal/task/conversation.go`) — this ADR does not change that cap. We confirmed persisted tool activity is UI-only: `conversationHistoryToChatMessages` (`internal/api/stage_conversation.go`) never replays `ToolActivity` back into a later turn's model context, only the single Draft-proposing `ToolCall` — so the 2KB cap costs no context budget and stays exactly as ADR-0018 set it.

Live-mode collapsing (revises ADR-0018's "considered and rejected" list, third-to-last bullet): while a sequence is still in progress, the most recent `LIVE_VISIBLE_COUNT` (3) calls render individually via `ToolActivityRow`, and anything older in that same sequence rolls into an expandable "N earlier tool calls" summary. ADR-0018 rejected a live incrementing-count chip because it "reads identically to nothing is happening" when the count is the *only* signal. That objection doesn't apply here: the in-flight call and its immediate predecessors stay individually visible and update in real time (spinner-equivalent pending state on the newest row) — only calls that have already scrolled out of recent attention get folded away, which is what keeps a long-running `ExecutePanel` sequence from becoming an unbounded wall of chips instead of hiding progress.

Layout: `.chat-history` (the class both panels already share) gets a bounded height (`max-height: 60vh; overflow-y: auto`) instead of growing the whole page, plus a new `useStickyAutoScroll` hook that scrolls to the latest content only while the user is already scrolled near the bottom — it never yanks them back down if they've scrolled up to read earlier history.

## Considered and rejected

* **Drop persisted tool-result content entirely** (metadata-only: name/success/byte-count, no text), to bound `conversation-{stage}.yaml` growth or model-context risk. Rejected on both counts: the file-growth risk is already bounded by the existing 2KB cap, and the context-budget risk doesn't exist — persisted `ToolActivity` is never replayed to the model at all (see above). Dropping content would also leave the drill-in tier with nothing to show for any historical turn.
* **Cap live drill-in content to the same 2KB persisted limit**, so live and historical always match exactly. Rejected: the frontend already holds the full untruncated content in memory for the duration of the live session; artificially truncating it to match what would survive a reload throws away detail for no benefit. The 2KB cap exists to bound *persistence* cost, not to limit what a live session may briefly hold.
* **Per-tool-type argument extraction for the list-tier preview** (e.g. surface `Read`'s file path specifically, `Bash`'s command specifically), for a more readable one-liner than raw truncated JSON. Rejected for this pass: the data model is deliberately tool-agnostic (`Name`/`Arguments`/`Result` strings, no structured per-tool schema surfaced to the frontend), and generic truncation of the raw arguments string covers every tool today without new per-tool frontend logic to maintain as tools are added.
* **Render drill-in results through the existing markdown renderer** (`react-markdown`/`rehype-highlight`), since it's already a dependency. Rejected: tool output isn't authored as markdown, and piping arbitrary file/command output through a markdown parser risks misinterpreting stray `*`/`#`/backticks as formatting. Plain monospace text is predictable.
* **Always force-scroll to the latest activity**, ignoring where the user has scrolled. Rejected as the classic "chat log yanks you back down while you're reading something above" annoyance; stick-to-bottom (scroll only while already near the bottom) is the standard pattern this ADR adopts instead.
* **A full per-tool-name breakdown in the summary chip** (e.g. `3 Read, 2 Bash`), rather than a plain count. Rejected: it starts duplicating the list tier one click away, working against the point of a compact collapsed state.
* **Unify `StageConversationPanel` and `ExecutePanel`'s underlying data models**, not just their rendering. Rejected as out of scope: they remain intentionally different concepts (paired turn-bundled activity vs. a flat, interleavable run trace, per `ExecutePanel`'s existing header comment and CONTEXT.md's Conversation/Execution distinction) — only the rendering/interaction layer needed to be consistent, not the data they're fed from.
