# Reject GitHub Issues as the task/project storage backend

Evaluated replacing `internal/task.FileStore`/`internal/project.FileStore` (plain YAML files under `data/projects/<projectId>/tasks/<taskId>/`, read/written via `os.ReadFile`/`os.WriteFile`) with a backend storing the same data as GitHub Issues, reached through the existing consumer-declared interfaces `TaskStore` (`internal/api/router.go:34`, ~20 methods) and `ProjectStore` (`internal/api/router.go:21`, 5 methods) — this seam already exists precisely so a provider like this could be swapped in (`docs/provider abstraction.md` lists Task/Project storage as an **Implemented** provider, though its interface names — `TaskLister`/`ProjectLister` — are now stale; the current code names are `TaskStore`/`ProjectStore`).

**Schema mapping is workable but nothing native comes for free.** `title` and `pull_request{url,number,branch}` map cleanly onto Issue fields Issues already have or a linked PR already provides. Everything else — `objective`, `constraints[]`, `assumptions[]`, `success_criteria[]`, `references{knowledge[],repo[]}`, plus `status` and `stage` (each a 6-value enum, tracked independently — no Issue analog for two orthogonal state axes on one object) — has no native Issue field, so the realistic approach is serializing the whole `Task` struct as YAML into the issue body (a front-matter blob) rather than decomposing into labels/milestones per-field. That's not a hard blocker, but it means Issues would be used as a generic blob store keyed by issue number, gaining none of GitHub's native structure (search-by-label, kanban-by-status) without also hand-maintaining labels in parallel with the body — two representations of the same state to keep in sync, a failure mode the current single-YAML-file model doesn't have. `id` is a further wrinkle: task ids are client-specified and checked for collision at `Create` time (`internal/task/store.go`'s `os.Stat`-then-write); GitHub issue numbers are server-assigned auto-increment integers, so preserving client-chosen slug ids means a label or body-embedded id plus a search-then-create round trip against the API — inherently less atomic than the current stat-then-write (itself already unlocked, but at least uncontended by network latency).

**The one thing this move might have promised — real, diffable history — is a net loss, not a gain.** `data/` is already tracked in this repo's own git history today (incidentally, since the app has no git-awareness), so every `task.yaml` change is already `git log`-able. GitHub Issues live in GitHub's hosted database, entirely outside any git repo; body edits show only an "edited" marker in the UI with no durable, API-queryable diff. This is the opposite direction from the sibling [git-backed-storage](../../data/projects/llm-workbench/tasks/git-backed-storage/task.yaml) task, which is evaluating making `data/` an *actual* git repository for real commit-level history — adopting Issues would move task storage further from that goal, not closer to it, and the two explorations should be read as pulling in opposite directions rather than complementary.

**Neither integration path fits `TaskStore`'s call volume cleanly.** The repo already has a working GitHub integration precedent — `internal/agentrunner/pr.go`'s `GitHubPRClient`, which shells out to the `gh` CLI (`runGH`, `exec.CommandContext(ctx, "gh", ...)`) and relies on ambient `gh auth` with no stored credentials (`docs/adr/0015-pr-feedback-delivered-as-a-file-not-a-live-tool.md`). That pattern fits its actual use — fetching PR comments once per task reopen — but `TaskStore` is called on nearly every API request (task list renders, polling, every stage transition), and a subprocess spawn plus a fresh `gh` auth handshake per call is a materially worse fit at that frequency than at PR-comment frequency. The alternative — a Go client library (e.g. `google/go-github`, optionally paired with `shurcooL/githubv4` for GraphQL batching) — avoids the subprocess cost and enables batching reads, but requires a stored PAT or App installation token the server reads at startup: this would be the first credential-storing provider anywhere in this codebase (today's LLM providers point at local LM Studio with no key; `gh` relies on the machine's own ambient auth), a real precedent shift in secret handling, rotation, and log redaction discipline that nothing else here has had to solve yet. Rate limits compound this either way: REST is capped at 5000 requests/hour authenticated, GraphQL on a points budget — both finite ceilings a local filesystem simply doesn't have, for a backend whose current call pattern was never designed against a quota.

**Verdict: don't adopt.** The schema mapping is workable but gains no native structure without hand-maintained duplication, the history win that would have been the strongest argument for this move is actually a regression relative to today (and moves directly against `git-backed-storage`'s direction), and both realistic integration paths force a tradeoff (frequent subprocess spawns, or the first stored credential in the codebase) that a storage backend called this often shouldn't need to make. If GitHub-visible task state is wanted for its own sake — e.g. stakeholder visibility once a task reaches `pr_review` — that's a much smaller, different feature (a one-way, opt-in mirror that opens or updates a linked Issue as a side effect of an existing transition) rather than replacing the source of truth, and would sidestep every concern above since it wouldn't need to satisfy `TaskStore`'s full read/write contract at all.
