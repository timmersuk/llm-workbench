# Generalize "executors are replaceable" into a cross-cutting provider pattern

The "providers are replaceable" invariant started out narrower, scoped just to executors ("executors are replaceable"). We generalized it into **provider**: a named pattern — any external system reached through a narrow, consumer-defined interface rather than depended on directly — applied uniformly across Execution's executor, Knowledge's future store, and Chat's LLM API, rather than re-deriving the same swappability argument separately for each. This is a naming/scope decision, not a new domain object: it doesn't sit alongside Task/Project/Knowledge/Execution, it's a pattern applied *to* them where they reach out to something replaceable.

Considered leaving the invariant scoped to executors only, and letting Knowledge's and Chat's swappable dependencies stand as unrelated, one-off design choices — rejected because the same interface-based-DI mechanism (narrow interface in the consuming package, concrete type never named outside it) already applied to all three, and naming the shared pattern once means any future provider-shaped dependency has a template to follow instead of re-justifying the same shape from scratch.
