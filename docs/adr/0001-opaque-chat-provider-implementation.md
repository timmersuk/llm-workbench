# Chat provider implementation is opaque by construction

`internal/chat`'s OpenAI-compatible client was a fully exported `Client` struct with exported fields (`BaseURL`, `APIKey`, `HTTPClient`), constructed via `NewClient` — nothing stopped a caller from depending on the concrete type instead of the `ChatCompleter`/`Completer` interfaces meant to keep it swappable. We're consolidating those two overlapping interfaces into one `ChatClient` (covering `CreateChatCompletion`, `StreamChatCompletion`, `ListModels`, `CheckHealth`), renaming the implementation to the unexported `openAIClient` with unexported fields, and renaming the constructor to `NewOpenAIClient` (naming the dialect explicitly, since `NewClient` didn't say which wire format it spoke). Making the concrete type unnameable outside `internal/chat` forces every consumer through the interface, which is the only way the "providers are replaceable" invariant actually holds in practice — an exported concrete type is an open invitation to bypass the abstraction the moment it's convenient.

Considered keeping `Client` exported and relying on convention/code review to stop direct use — rejected: once a caller depends on the concrete type, the interface boundary stops being enforced by the compiler, and swapping the implementation later means hunting down and fixing every place that snuck through.
