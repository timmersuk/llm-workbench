# Reuse Conversation/Draft/Finalize for Review, instead of a bespoke review mechanism

Milestone 6 needed to decide how a human reviews a completed execution's diff. Two real alternatives were on the table: a plain human-only approve/reject form (no AI conversation at all), or a dedicated `ReviewConversation` type built specifically for review's needs. We chose neither — Review reuses the exact same Conversation → Draft → Finalize mechanism GrillMe and Planning Mode already built in Milestone 4 (`internal/task/conversation.go`, `internal/drafttool`, `internal/api/stage_conversation.go`, `StageConversationPanel.tsx`), just with a new stage (`review`), a new Draft tool (`propose_review`), and a new Finalize function (`FinalizeReview`).

The stage-conversation HTTP routes are already generic over `stage` (`internal/api/router.go:98-102`), and the only stage-specific switches (`validateConversationStage`, `stageTool`, `buildStagePrompt`) are small, additive `case` branches — so this reuse costs little to build. It also lets the agent do real work during review (run automated checks, walk verification steps, discuss findings with the human) rather than just present a diff and wait for a click, which a plain approve/reject form couldn't offer without inventing its own conversational layer anyway — at which point it wouldn't really be simpler, just a parallel implementation of the same idea.

The tradeoff: Review's Draft is structurally different from GrillMe/Planning's. Those propose a *new* artifact (context.yaml, plan.yaml) that Finalize always advances `stage` forward into. Review's Draft is a three-way decision (`approved | rejected | needs_changes`) about a *prior* artifact (the execution's diff), and Finalize can move `stage` in either direction depending on that decision — the first time Finalize hasn't been purely forward-only (see `CONTEXT.md`'s **Finalize** entry, updated alongside this ADR). We accepted that asymmetry rather than forcing Review into looking identical to GrillMe/Planning, because the alternative (a bespoke mechanism) would have meant maintaining two separate conversation/draft plumbing layers for what's fundamentally the same interaction shape: an LLM proposes, a human decides, the decision is durably recorded.

This is hard to reverse once `propose_review`/`ReviewPanel`/`FinalizeReview` exist and other code depends on Review looking like Requirements/Planning — and it sets precedent: the next stage that wants "AI assists, human decides" should follow this same shape rather than re-litigating the question.
