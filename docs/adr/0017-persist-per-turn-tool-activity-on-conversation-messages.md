# Persist per-turn tool activity on the conversation message, capped, not as a separate live-only stream

Stage conversations (GrillMe/Planning Mode/Review) run an agent turn that can make several read-only (and, for Review, Bash) tool calls before producing its final content or Draft. Today that intermediate activity is either dropped entirely (`ClaudeRunner.Run`'s `processMessage` silently ignores `ToolUseBlock`/`ToolResultBlock`) or, for the `ChatClientRunner` path, streamed transiently as `chatToolActivityEvent` SSE events that no frontend panel renders and that vanish on reload. Users have no visibility into what the agent is doing during the long gap before its first reply, and that gap is worse than it needs to be because the executor most stage conversations actually run on (`ClaudeRunner`, preferred whenever healthy) doesn't even forward the activity it already receives from the `claude` CLI's own message stream.

We're closing both gaps together: `ClaudeRunner.Run` will forward non-Draft tool calls/results through `RunInput.OnToolCall`/`OnToolResult` (mirroring how `Execute`'s `processExecuteMessage` already does this), and `ConversationMessage` gains a persisted `ToolActivity []ConversationToolActivity` field — the ordered `{name, arguments, result, is_error}` list for the turn, attached to the assistant message that closes it out. This is a deliberate departure from treating tool activity as purely transient: revisiting a stage's conversation (a normal, expected flow per **Revise**) should show what the agent did on every past turn, not just the current live one.

Persisted arguments/results are capped at a fixed size (independent of whatever cap the live SSE stream applies), with the existing `[truncated: ...]` marker convention `internal/toolloop/tool.go`'s `truncateResult` already uses. This matters specifically because `conversation-{stage}.yaml` is read and rewritten in full on every single `AppendConversationMessages`/`ReplaceConversationMessages` call (`internal/task/conversation.go`) — an uncapped `Read` of a large file via the claude-code path (which has no `toolloop`-level truncation to rely on, unlike the `ChatClientRunner`/`toolloop.Engine` path) would otherwise grow that file, and its per-turn rewrite cost, unboundedly over a long session.

Considered and rejected:

* **Keep tool activity purely live/ephemeral** (fix the `ClaudeRunner.Run` gap, but don't touch the persistence schema). Rejected: it solves "why is nothing happening right now" but not "what did the agent already do," which matters just as much once a user reopens a stage's conversation later — the whole point of a Conversation being reopenable (see **Revise**, `CONTEXT.md`) is that prior context, including what the agent looked at, should still be visible.
* **One separate `ConversationMessage` per tool call/result** (an OpenAI-style `role: "tool"` entry interleaved into `Messages`), instead of bundling onto the assistant message. Rejected: the underlying message stream already flattens a turn's text into one accumulated string with no preserved interleaving against tool calls (`processMessage`/`processExecuteMessage` both do this), so there's no finer-grained ordering to actually preserve — bundling onto the one assistant message matches both the data available and the UI's "one summary chip per turn" grouping directly, without the frontend needing to re-scan and re-group a flat list.
