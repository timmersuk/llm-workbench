# `internal/api` handlers become methods on a single, package-internal `Server` struct

`NewRouter` (`internal/api/router.go:91`) grew to 9 parameters, and several handler families — most visibly `handleStartStageConversation`/`handlePostStageMessage`/`handleRegenerateStageMessage` (`stage_conversation.go`) at 7 params each — re-pass an identical handful of process-invariant dependencies (`ProjectStore`, `TaskStoreFactory`, `agentRunners`, `reposRoot`, `prClient`, `defaultBranchResolver`, `knowledgeReader`) to every call site, unchanged from one call to the next. Every cross-cutting dependency Milestones 6, 7, 8, and 8a each added made every one of these signatures longer, not just the function that actually needed the new thing (`docs/milestones/done/milestone8b.md`).

We're collapsing this into a single `Server` struct (`internal/api`, unexported) holding every invariant dependency as a field, constructed once inside `NewRouter`. Every HTTP handler becomes a method on `*Server` instead of a free function closing over a fresh copy of the same parameter list. The five internal helpers that mix invariant and per-call arguments the same way (`resolveStageRun`, `buildReviewContext`, `buildRejectedReviewContext`, `buildStagePrompt`, `resolveStageStreamTarget`) become `*Server` methods too — leaving them as free functions taking the struct (or its fields) as a parameter would just move the same re-passing problem one level down the call stack instead of removing it.

Considered and rejected:

* **Splitting into multiple structs by route family** (e.g. task/stage-conversation vs. project vs. execution/review vs. chat). Rejected: the chat handlers are the only family with a visibly smaller dependency set, and even they need only a strict subset of the same union `NewRouter` already takes — nothing needs a dependency *outside* that union. Splitting would mean deciding which sub-struct owns which handler, and occasionally wiring two structs into one handler that spans families, for a benefit (smaller per-concern interface) nothing is currently paying for.
* **Exporting `Server`/`NewServer` and having `cmd/server/main.go` construct it directly**, replacing `NewRouter` as the public entrypoint. Rejected: `NewRouter` has exactly one call site (`cmd/server/main.go:77`) and will only ever have one. Exporting `Server` buys flexibility nothing is positioned to use, at the cost of touching `main.go` for a change with no external behavior difference. `NewRouter`'s public signature is unchanged; it builds the unexported `*Server` internally and returns the `http.Handler` as before, so the refactor is verifiable as `internal/api`-only from the outside.
* **A test-builder helper** for constructing `Server` values in tests. Rejected: named-field struct literals already solve the problem a builder would solve — a test can just omit whatever fields it doesn't need, instead of today's positional calls padding irrelevant args with `nil`/`""`. A local builder in one test file is a cheap follow-up if real repetition shows up later, but not worth committing to upfront.
* **Migrating incrementally** (new struct introduced alongside the existing free functions, routes moved over one at a time). Rejected: this refactor is purely internal and behavior-preserving — nothing about it is independently shippable, so there's no partial-delivery value to capture, only a straddling period where two calling conventions coexist in one package for no benefit. Done in one pass, single PR, backed by the existing handler test suite as the safety net.

Explicitly out of scope: `internal/agentrunner`'s workspace resolvers (`ResolveWorkspace`/`ResolveExecutionWorkspace`/`ResolveReviewWorkspace`). They mix `reposRoot` (process-invariant) with `repositories` (varies per-*project*, not per-call) — a structurally different shape from `internal/api`'s "identical value on every single call" case, and don't share the problem this decision solves.
