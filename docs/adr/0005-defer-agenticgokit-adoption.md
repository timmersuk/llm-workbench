# Defer adopting AgenticGoKit for agent orchestration

Evaluated `github.com/AgenticGoKit/AgenticGoKit` (a Go multi-agent orchestration framework: Sequential/Parallel/DAG/Loop workflow patterns, a unified LLM-provider abstraction, tool-calling, and built-in memory/RAG) as a way to reduce the hand-rolled code in `internal/agentrunner` and `internal/chat`. Decided not to adopt it now: this repo's executor abstraction (`docs/provider abstraction.md`) spans Claude Code, Codex CLI, local LLMs, external automation tools, and human developers as opaque black boxes (`docs/project_summary.md` §7) — AgenticGoKit only models LLM-agent calls, and its Anthropic support is a plain chat-completion client, not a driver for the `claude` CLI subprocess that `ClaudeRunner` actually wraps via `severity1/claude-agent-sdk-go`. The repo's real "workflow" is the Task stage state machine (Requirements → Architecture → Planning → Implementation → Review → Completion), a human-supervised, YAML-persisted state machine — not the autonomous multi-agent DAG AgenticGoKit orchestrates; today's turn-taking is one `AgentRunner.Run` per human chat message. Adopting it would also reintroduce the per-vendor adapter layer that ADR 0004 already rejected, and would add a beta-stage (v1beta API, still churning) third-party dependency to save a comparatively small amount of already-working, tested code.

Considered adopting it now for its tool-calling/session/provider-abstraction surface — deferred, not rejected outright: if the workbench later needs genuine autonomous multi-step agent orchestration (an executor that plans and runs several sub-steps itself without a human turn in between, rather than one `Run` call per human chat message), AgenticGoKit's DAG/Sequential/Parallel primitives would become directly relevant and this decision should be revisited then.
