# Close the Claude/Codex live tool-activity and thinking drop gaps; extend ADR-0017 to Codex

ADR-0017 designed persisted Tool Activity but didn't fix the live gap for the CLI-backed executors: `ClaudeRunner.Run` explicitly ignores `RunInput.OnToolCall`/`OnToolResult` (`internal/agentrunner/claude_runner.go`, `processMessage`'s switch has no forwarding path), and `CodexRunner.Run` has no such wiring at all — so a stage conversation (GrillMe/Planning/Review) running on either executor shows nothing between the user's message and the agent's final reply, however long that gap is. Separately, `processMessage`/`processExecuteMessage` have no `case` for `claudecode.ThinkingBlock` (from `github.com/severity1/claude-agent-sdk-go`), and `streamDeltaText` only reads `delta["text"]`, never `delta["thinking"]` — both silently drop Claude's extended-thinking content if it were ever enabled. We're closing all of these together: `ClaudeRunner.Run` and `CodexRunner.Run` both forward tool call/result through `OnToolCall`/`OnToolResult` (mirroring `processExecuteMessage`'s existing `tool_call`/`tool_result` handling, and `ChatClientRunner`'s existing wiring into `toolloop.Engine`), and the two thinking drop points get real `case`s that feed the existing `chat.Delta.ReasoningContent` field — the same "Thinking" panel `ChatPanel.tsx`/`StageConversationPanel.tsx` already render for the OpenAI-SDK path.

Frontend: `frontend/src/StageConversationPanel.tsx` gets a live tool-activity list reusing `ExecutePanel.tsx`'s existing pattern verbatim — closed-by-default `<details className="thinking-panel">` chips, one per call/result, appended in order as SSE events arrive — stacked between the Thinking panel and the message content. Once the turn closes (live or reopened later), it collapses to the single "Used N tools" summary CONTEXT.md's **Tool Activity** entry already describes; the two are different views of the same list; see CONTEXT.md.

Alongside the tool-activity/thinking fixes, `StageConversationPanel`/`ChatPanel` also gain three lightweight liveness indicators for the duration a turn is in flight (existing `sending` state), independent of executor or of whether that turn happens to make any tool calls at all: an animated "working" indicator, an elapsed-time-since-turn-start counter, and a token counter. The token counter is the only one with a real design question — neither backend integration exposes a live running token count (OpenAI-SDK streaming's `chunk.Usage`, `internal/chat/client.go:200`, only arrives on the single final chunk; Claude's CLI `ResultMessage.Usage` only arrives once the whole run completes) — so it's a client-side heuristic estimate (~chars÷4) computed from accumulated content/reasoning text as it streams, labeled `~` to mark it as approximate, then snapped to the real number once the turn's final usage lands. The working indicator and timer need no such approximation — both are pure frontend state derived from "a turn is in flight," with no backend change required.

## Considered and rejected

* **Enable extended thinking now** (`claudecode.WithMaxThinkingTokens`), since we're touching the drop points anyway. Rejected: it's a distinct cost/latency decision (more tokens, slower turns, on every stage-conversation call) independent of "stop dropping what we already receive." The drop-point fixes are forward-compatible no-ops until that separate call is made.
* **Claude-only fix, leave Codex as-is.** Rejected: `CodexRunner.Run` has the identical gap and the identical fix shape; skipping it leaves the same silent-pause bug in the other CLI-backed executor for no real savings.
* **Reuse the existing 16KB `maxToolResultBytes` cap (`internal/toolloop/tool.go`) for persisted Tool Activity.** Rejected: that cap was sized for a small model's context window (Milestone 8 grill), not a human skimming a reopened conversation, and 16KB × many calls × many turns is exactly the unbounded `conversation-{stage}.yaml` rewrite cost ADR-0017 already flags. Persisted arguments/results are capped at ~2KB instead, same `[truncated: ...]` marker convention.
* **A single live "Used N tools" chip that increments in place**, matching the persisted/at-rest shape everywhere. Rejected as the *live* rendering: it reads identically to "nothing is happening" if the user glances away and back, since no new element appears — the whole point of this ADR is a visible per-call signal during the gap. Kept as the *at-rest* rendering (turn closed, or reopened via Revise), where a full blow-by-blow list is noise rather than signal.
* **Show the token counter only once the turn completes** (the real, exact number, no live estimate). Rejected: accurate but not actually live — it would sit blank for the whole in-flight duration, which is the opposite of what this ADR is for. The heuristic-then-snap approach keeps the number moving during the gap and still ends up exact.
* **Stream Claude's raw extended-thinking text live, à la Claude's own UI reasoning toggle.** Rejected for this pass — same reasoning as leaving `WithMaxThinkingTokens` off above: verbose raw reasoning output is a separate, heavier feature than the lightweight "is it still working" signals (spinner, timer, approximate token count) this ADR actually targets.
